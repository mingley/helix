# Siraj variant-pair endpoint: source-semantics review

This is a review of source metadata and producer code. It does not establish a usable outcome endpoint by itself. We inspected only the first two rows of the S20 worksheet, not S20 outcome rows. The workbook reader loaded the workbook's shared-string table, so this does not claim that no unselected strings were instantiated. The public article and source code were inspected for design and semantics, not for numerical outcome performance. A later bounded range read of the upstream compressed source produced its header and instantiated 63 bytes beyond its first newline without printing those bytes; see the provenance below.

## Design and available columns

Siraj et al., *Functional dissection of complex trait variants at single-nucleotide resolution*, Nature (2026), [doi:10.1038/s41586-026-10121-6](https://doi.org/10.1038/s41586-026-10121-6), Methods, states that 2,522 pairs of fine-mapped trait-associated variants within 150 bp were selected with PIP > 0.1 and a CRE overlap requirement. For up to six 200-bp windows around each pair, four oligonucleotides were designed: Ref/Ref, Alt/Ref, Ref/Alt and Alt/Alt. Selection is trait- and annotation-enriched and is not a random sample of human regulatory DNA. The [design audit](../../epistasis-source-audit/README.md) checks exact four sequences and variant IDs, but does not verify assembly against a reference or match them to outcome rows.

S20 in the cached publisher supplement workbook `S30-bundle.xlsx` (SHA-256 `3e62a3876b70e9c75951df26ed09ba552c3ba6f9f3b318934c1b01a5a42403b1`) has `Variant 1`, `Variant 2`, `Distance`, `Cell Type`, four meta Log2FC columns and four groups of six per-window columns named `Log2FC_{refref,altref,refalt,altalt}_var{1,2}_{left,middle,right}`. It also has activity and emVar call columns. Column names suggest the needed measurements but do not alone prove that each field has literal allele orientation, identical normalization, or common library selection. Meta estimates from different windows cannot replace four matched measurements from one window without establishing their weighting and compatibility.

The [official supplement PDF](https://media.springernature.com/original/springer-static/esm/art%3A10.1038%2Fs41586-026-10121-6/MediaObjects/41586_2026_10121_MOESM1_ESM.pdf), SHA-256 `3170c18e98b69ce9649ca3233a3639e2c4a58578f145f02bfc06181e8306c865`, provides only the short legend “Supplementary Table 20: Summary of variant pair results”; it does not resolve these column-level questions. The article Methods text is retained at `research/variant-transfer/source/siraj2026-methods-metadata.json`.

## Normalization, replication, and sign

The article says that barcode counts were summed over oligonucleotides and that MPRAmodel used DESeq2, independent dispersion estimates for each cell type and library, and per-library summit-shift scaling that centres the RNA/DNA ratio distribution at one. The measured element activity is the log2 fold change for RNA relative to DNA. Its diplotype analysis used stricter filtering, described as excluding variants with fewer than 100 DNA counts or fewer than 10 RNA counts across all four diplotypes. When variants were assayed in multiple libraries, the library with the highest sum of square roots of reference and alternate plasmid counts was selected. Separate replicate transfections are described in Methods; the S20 headers do not expose per-construct replicate estimates, library identifiers, uncertainties or counts. The producer code and upstream header described below provide stronger evidence of joint per-library selection; the publisher workbook has not been independently compared row by row to that upstream output, and the generation of the upstream row has not been reconstructed. These limits should be explicit when interpreting the four-value contrast.

The Methods describe an interaction as expected additive effect **minus** the observed double-allele effect, and separately recode alleles for their interaction analysis according to measured activity. For a fixed genomic reference, the proposed contrast is `E = activity(AltAlt) - activity(AltRef) - activity(RefAlt) + activity(RefRef)`; under the same literal allele orientation and normalization this is the negative of the stated expected-minus-observed contrast. Changing a single reference/alternate orientation reverses the sign, so do not infer a signed biological direction from the headers alone. The null `E = 0` is invariant to either reversal, but absolute values, missingness, and common source scale remain material. Do not filter on S20 `any_active`, `any_emVar`, or `int_emVar` calls when defining a pre-outcome cohort.

## Producer code review and unresolved handoff

At public producer repository commit [`1e38d1e3d4414dfa3a62b22110eba0136eda197d`](https://github.com/julirsch/finemapped_mpra/tree/1e38d1e3d4414dfa3a62b22110eba0136eda197d), `code/fig3/haplos_preprocess.R` reads `all_windows.txt.gz`, parses construct IDs into variant 1, variant 2, centred variant and window, and retains source `refref`, `refalt`, `altref`, and `altalt` Log2FC fields. `code/fig3/haplos_ints.R` separately creates activity-ranked `_recode` and `v1inc/v2dec` fields from meta Log2Skew values. The GitHub snapshot's `code/fig3/fig3_file_overview.R` references `code/tables/table20.R`, which is absent from that snapshot. The three GitHub source files have SHA-256 values `55cfb3e52f964f44036ddae7bf044f554220d91967919d4645c1b1fcdb895744`, `1b6e8231cf173c3b98be1f64cefaf912ce38f569e725539fcf39e93e5e65961f`, and `afce4b08c2434d953f92e861114a417d028f36edcef40e25a2ca12238612d2d6`, respectively.

A separate [Zenodo `code.zip`](https://zenodo.org/api/records/15297965/files/code.zip/content), record 15297965, SHA-256 `0232a4ab60d0fec6eb3f1f3ed1ba0cbe08920fca821647beafc2c0b665b9b87e`, contains `code/tables/table19.R`, SHA-256 `7c8cf5a9dfbee240ec7fbe495b1afb69f58910d42ad67b89726daca5a8820697`. Despite the numbering difference, the table19 script produces column names and structure matching publisher S20. It groups upstream rows by the pair, centre, window and cell type; scores a row by the sum of square roots of the four mean plasmid counts; retains one maximum-scoring row; directly renames its four `refref_Log2FC`, `altref_Log2FC`, `refalt_Log2FC`, and `altalt_Log2FC` values; and pivots windows into columns. It does not perform the activity-ranked recoding described above. The archive's `table20.R` instead exports recoded non-additive fields and does not match publisher S20's header. This clarifies the mismatch with the GitHub overview, while the published workbook has not been independently compared to the output of that script.

The upstream file named by `haplos_preprocess.R` is present in [Zenodo `data_preprocess.zip`](https://zenodo.org/api/records/15297965/files/data_preprocess.zip/content). Its ZIP central directory was fetched with a 65,536-byte HTTP range, not by downloading the 970,231,136-byte archive. The member `data/preprocess/haplos/all_windows.txt.gz` has an uncompressed member size of 24,977,428 bytes (it is itself gzip-compressed) and ZIP local offset 945,248,247. A 16,384-byte range at that offset was processed only far enough to emit the gzip TSV header. The 859-byte header lists one `library`, `cell_type`, all four `*_Log2FC` and `*_Log2FC_SE` fields, four mean plasmid and four mean RNA counts, and construct/window IDs. Streaming decompression buffered 63 bytes beyond the first newline, which were not printed. Thus the producer selection code takes its four values together from a row with a single library field, supporting common-library interpretation under the source schema. Header and code inspection do not establish row-by-row equality to the publisher S20 values, the correctness of an upstream producer, or replicate-level support. None of the 85 R, Python or shell source files in the inspected Zenodo code archive was found to generate `all_windows.txt.gz`; that generation remains unresolved.

The GitHub source repository is GPL-3.0; this report describes behavior without incorporating its code into the implementation. The publisher article and separate Zenodo deposit have distinct licensing terms, already documented in `research/variant-transfer/source/README.md`.

The source has promising four-construct design and evidence of a common selected library. Exact identities and common-window linkage, source-derived complete-case semantics, publisher workbook-to-upstream equality, and per-replicate support must still be established or explicitly scoped before biological conclusions. Existing work has examined other source outcomes; any follow-on analysis must document that exposure rather than claim a wholly unexposed study.
